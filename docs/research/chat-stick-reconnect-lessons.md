# chat-stick reconnect and audio lessons

Source inspected: `steveruizok/chat-stick` at pinned commit [`3321c9bfc9771ee8b3adc4815f6c72890d3db125`](https://github.com/steveruizok/chat-stick/tree/3321c9bfc9771ee8b3adc4815f6c72890d3db125). The comparison target is our current `firmware/main/network_relay.c` and `firmware/main/offline_echo.c`.

## Highest-value conclusions

1. **Keep our ownership boundaries, but make the WebSocket callback fully nonblocking.** Our audio task owns codec I/O and hands capture to `network_relay_capture()` through zero-wait queue operations (`offline_echo.c:100-123`, `network_relay.c:797-865`). That is better than chat-stick's callback/main-loop coupling. However, our disconnect callback calls `reset_stream_state()`, which can wait forever on `stream_mutex` (`network_relay.c:173-186,313-321`). Have the callback set an event/generation only; let the relay manager own queue resets and session teardown.
2. **Add an explicit connection generation and response turn identity.** chat-stick's server increments `sessionGeneration` and makes old socket callbacks return early after replacement ([device socket](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/server/src/live-session.ts#L292-L399), [upstream socket](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/server/src/live-session.ts#L445-L503)); this is its strongest reusable ownership pattern. Firmware distinguishes socket-open from server/session-ready and rejects a stale `turn_complete` until response audio has arrived, but it has no wire turn ID and therefore only mitigates stale events heuristically ([callbacks](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L117-L140), [guard](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/TurnController.cpp#L58-L71)). Our input `turnId` is a good start (`network_relay.c:582-623`), but inbound control/audio is not scoped to it. Tag every queued playback item and control transition with a connection generation plus server response/turn ID; discard mismatches after reconnect or barge-in.
3. **Use local-first, generation-scoped cancellation.** chat-stick stops queued playback before starting capture, and separately handles server `drop_audio` by flushing the old tail without leaving Recording ([start](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1414-L1441), [drop callback](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L129-L140)). Our urgent `COMMAND_RECORD_START` already interrupts playback between small writes (`offline_echo.c:361-389,438-489,740-753`). Preserve that immediate local action, then send a remote cancel tied to the old response generation; do not rely on an unscoped `drop_audio` message.
4. **For network playback, copy bounded data in the receive path and let the audio task drain it.** chat-stick's mutex-protected ring, prebuffer gate, completion escape hatch, and dedicated playback task are useful shapes ([ring enqueue](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L425-L460), [playback gate](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1600-L1625), [task](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L648-L779)). Do not run codec writes, UI work, or unbounded waits in our WebSocket event task.
5. **Our transport liveness is stronger, but protocol liveness is incomplete.** chat-stick retries a disconnected socket every fixed five seconds and times out a socket that opens but never reaches AI-ready ([reconnect](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/services/LiveSessionService.cpp#L377-L402), [ready timeout](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1707-L1722)). Our ESP-IDF client already configures WebSocket ping timeout, TCP keepalive, and automatic reconnect (`network_relay.c:464-487`), but sends only one application ping and never timestamps/validates its pong (`network_relay.c:636-667`). Add a ready deadline and recurring application heartbeat with a missed-pong deadline; use capped exponential backoff with jitter for fleet safety.

## Patterns worth reusing

### Connection and session state

- chat-stick rotates configured server endpoints on each connection attempt and remembers the last successful endpoint ([connect rotation](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/services/LiveSessionService.cpp#L309-L352), [success on open](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/services/LiveSessionService.cpp#L656-L678)). Reuse the idea only if we add multiple relay endpoints. Our strongest-visible-network scan and full Wi-Fi/WSS restart after loss (`network_relay.c:369-461,628-690`) already cover the current topology.
- Socket-open is not treated as application-ready: connection status remains Connecting until `server_ready` or `ready`, and a 20 s deadline forces a reconnect if readiness never arrives ([callbacks](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L112-L128), [constant](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppController.h#L62-L76)). Our `SOCKET_CONNECTED_BIT` / `SOCKET_READY_BIT` split already models this (`network_relay.c:32-37,239-245,304-321`); add the missing deadline and make readiness connection-generation-specific.
- Response completion is accepted only after audio, playback starts after a prebuffer threshold or after a complete short reply, and Ready is reached only after Playing drains ([turn guard](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/TurnController.cpp#L58-L71), [playback transitions](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1600-L1644)). These guards should become explicit states in our future online playback path, backed by IDs rather than used as the only stale-event defense.

### Capture and playback queues

- chat-stick buffers the first 150 ms before committing a press, then sends the start marker followed by retained audio; a short tap never becomes a server turn ([constants](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppController.h#L72-L102), [commit and buffer](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1475-L1524)). Our 180 ms precommit ring already implements the better streaming form without losing the prefix (`offline_echo.c:318-353,585-619`). Keep it.
- Our capture transport boundary is stronger: `offline_echo` invokes the sink from its audio-owner task, while `network_relay_capture()` copies frames into a bounded queue without waiting and reserves two slots for commit/cancel (`network_relay.c:48-50,797-865`). Preserve the control reserve and observable drop/high-water counters. Add one missing invariant: if `OFFLINE_ECHO_STREAM_START` is rejected, latch that the network turn was not accepted and do not pretend later audio/commit belongs to a live turn (`offline_echo.c:327-346`).
- chat-stick's server also demonstrates explicit queue budgeting: it caps not-yet-forwardable capture audio, drops oldest chunks to stay within budget, atomically detaches the queue before flushing, and rejects binary audio when the input turn is closed ([queue](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/server/src/live-session.ts#L1055-L1086), [turn gate](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/server/src/live-session.ts#L1185-L1217)). Reuse the explicit byte budget and turn-open gate; choose and count the drop policy deliberately.
- For response audio, adopt a bounded ring plus an explicit start threshold and “turn complete with any audio” escape hatch. Queue overflow must be a visible turn failure or controlled drop policy, not silent state progress.

### Cancellation and failure handling

- A new press first clears local playback; server `drop_audio` clears any remaining old tail while capture state stays unchanged ([local stop](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1414-L1441), [wire dispatch](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/services/LiveSessionService.cpp#L741-L755)). This separation is reusable. Our mute path already clears rings, mutes output, and sends capture cancel when appropriate (`offline_echo.c:529-545`). Extend it to assistant-response cancellation.
- chat-stick rate-limits repeated capture-failure logs, caps recording duration, and applies a 15 s response timeout that flushes playback ([capture reporting](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/TurnController.cpp#L75-L97), [recording and response timeouts](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1551-L1584)). Our snapshots already count codec, queue, protocol, and transport failures. Add per-turn terminal failure reasons and a deadline for response start/drain rather than merely logging dropped frames.

## Board/framework-specific or unsafe patterns not to copy

- **No automatic runtime Wi-Fi recovery.** chat-stick calls `connectKnownNetworks()` during initial/retry flows, but its steady loop only reconnects WebSocket when `WiFi.status()` is already connected ([startup](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L420-L442), [loop gate](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L369-L379)). Our event-driven IP-loss exit, WSS teardown, rescan, and reconnect loop is the reusable baseline.
- **No post-ready liveness watchdog.** Ping/pong events are ignored, while `/ping` is a separate blocking HTTP probe ([event handler](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/services/LiveSessionService.cpp#L656-L683), [HTTP ping](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/services/LiveSessionService.cpp#L416-L439)). Do not infer a healthy session from `_connected` alone.
- **Fixed reconnect intervals and optional insecure TLS.** A uniform five-second retry has no exponential backoff or jitter, and endpoints without a CA certificate call `setInsecure()` ([retry constant](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/services/LiveSessionService.h#L311-L327), [TLS setup](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/services/LiveSessionService.cpp#L333-L347)). Keep our certificate bundle and hostname check; add randomized backoff.
- **Half-duplex Arduino I2S reconfiguration.** Recording disables the speaker amp and rebuilds I2S at 16 kHz; playback rebuilds it at 24 kHz ([record switch](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L241-L280), [reconfigure](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L551-L609)). It supports button interruption but rules out true simultaneous capture/playback and AEC. Our ESP-IDF duplex 24 kHz codec setup (`offline_echo.c:206-305`) is the correct board-specific base.
- **Blocking capture and overloaded WebSocket callbacks.** A 100 ms `i2s.readBytes()` runs in the main loop ([capture](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L282-L325)); inbound audio callback work copies into a mutex-protected ring, advances state, and services UI, with a comment acknowledging that one `poll()` may stay inside the callback burst for the whole response ([callback](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L233-L244)). Do not reproduce this on the ESP-IDF event task.
- **Playback overflow/state inconsistency.** `queuePlayback()` drops an entire frame on overflow, but its caller ignores the return and still marks response audio received ([overflow](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L425-L460), [caller](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L233-L238)). Also, `stopPlayback()` clears the in-flight flag even though a 20 ms I2S write may still be executing in the playback task ([flush](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L535-L549), [writer](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L717-L779)). Our owner task should acknowledge cancellation at a chunk boundary and expose when the old generation is actually quiescent.
- **Heuristic stale-turn defense without wire IDs.** Ignoring `turn_complete` until audio arrives is a useful secondary guard, not a substitute for response identity. Late binary audio itself is untagged in chat-stick ([binary/control dispatch](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/services/LiveSessionService.cpp#L686-L755)). Do not carry that ambiguity into our relay protocol.

## Suggested next-work order

1. Remove blocking reset work from `websocket_event_handler`; introduce manager-owned connection generations and reset.
2. Add ready and recurring pong deadlines plus jittered capped reconnect backoff.
3. Define response/turn IDs on every inbound control and audio frame; tag playback queue entries and cancellation with them.
4. Add the bounded inbound playback ring and have the existing audio task exclusively drain/cancel it; retain local-first barge-in.
5. Make queue overflow, rejected stream start, send failure, timeout, and cancellation terminal/observable per-turn outcomes.

## Implementation status

The first two reconnect increments were implemented after this review. WebSocket callbacks no longer call the blocking stream reset; manager-owned explicit clients carry monotonically increasing epochs through `hello`/`ready` and capture/echo bookkeeping. Connect, protocol-ready, and nonce-checked pong deadlines now trigger destroy/recreate with capped jittered backoff, plus a bounded prototype session lifetime. A rejected or failed capture stream is latched and cancelled rather than emitting later frames as though its start succeeded. Remote forced-close, Worker-deployment, and suppressed-pong tests all reached a new ready epoch without reboot, with successful PCM turns after recovery. Response IDs, inbound playback, and response-scoped cancellation remain next.
