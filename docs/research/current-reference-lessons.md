## Executive summary

Both references make display-buffer ownership explicit. StackChan renders into a small **internal-RAM** DMA draw buffer, while chat-stick synchronously pushes its PSRAM framebuffer through Arduino_GFX. Our later inspection showed that the previously credited `lv_draw_buf_flush_cache()` call is a no-op with LVGL's default software canvas handlers; the canvas is CPU-read into a separate display buffer. The stronger risk was asynchronous QSPI transfer ownership in the BSP; a project-owned flush driver now resolves it by waiting for `on_color_trans_done`. Both projects also deliberately **throttle rendering while audio is active** (chat-stick: 90 ms minimum frame spacing during playback; StackChan: avatar tick drops from 20 ms to ~120 ms while the voice agent is non-idle). chat-stick's turn state machine remains worth adopting; its half-duplex I²S teardown/reinit must not be. Neither reference drives the mouth from playback audio — our RMS-envelope mouth remains ahead of both.

## 1. Framebuffer ownership and PSRAM cache coherency

**chat-stick (Waveshare target).** The text UI allocates a full 368×448 RGB565 framebuffer plus a previous-frame copy in PSRAM ([TextDisplay.cpp#L28-L49](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/ui/TextDisplay.cpp#L28-L49)). Every flush diffs rows with `memcmp`, computes one dirty rect, and falls back to a full-screen push when the rect exceeds a third of the panel ([flushFrame, TextDisplay.cpp#L227-L321](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/ui/TextDisplay.cpp#L227-L321)). Crucially the push is `Arduino_GFX::draw16bitRGBBitmap()` on a QSPI bus object ([Board.cpp#L12-L17](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/hal/Board.cpp#L12-L17)) — the CPU reads the PSRAM buffer through the cache, so stale-cache blanking cannot occur. The diff-then-flush pattern is worth borrowing; the coherency safety is an artifact of CPU-pushed transfers and does **not** transfer to our esp_lcd/DMA path.

**m5stack/StackChan.** The avatar is not rasterized at all: eyes, eyelids, and mouth are LVGL container objects with rounded radii, moved and scaled per frame ([eyes.cpp#L18-L52](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/stackchan/avatar/skins/default/eyes.cpp#L18-L52)). The LVGL port is configured with a **20-row partial draw buffer in internal DMA-capable RAM** — `buffer_size = width_ * 20`, `double_buffer = false`, `buff_dma = 1`, `buff_spiram = 0` ([stackchan_display.cc#L130-L156](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/hal/board/stackchan_display.cc#L130-L156)). DMA never reads PSRAM, so coherency is structurally impossible to get wrong.

**Lesson for us.** Do not infer cache safety from API names. `lv_draw_buf_flush_cache()` only acts when that draw buffer's handlers provide a callback; our default software canvas handlers do not. More importantly, the panel-facing partial buffer must not be reused until asynchronous QSPI completion. StackChan's internal DMA-buffer model informed the first implementation, but physical testing exposed a separate CO5300 rate/burst limit: successful callbacks continued after the panel had gone black. A 220-row complete-face buffer initially held traffic near 28 transactions per second, but could not coexist with the linked Wi-Fi/TLS stack in contiguous internal RAM. The network build therefore uses a completion-owned 110-row buffer and enforces at least 35 ms between **every** submission; this removes paired bursts, remains near the proven ~28-transaction/second envelope, and passed a visible 4,400-transfer soak.

## 2. Display refresh cadence and backpressure under audio load

- chat-stick renders only when dirty and, **while playback is active, enforces a minimum 90 ms frame spacing** (`kPlaybackRenderFrameMs`, [AppController.h#L93-L94](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppController.h#L93-L94); gate in [renderIfNeeded, AppControllerImpl.h#L1755-L1776](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1755-L1776)). Its main loop also suppresses power polling, heartbeat logging, header refresh, and Wi-Fi polling while `AppState::Playing` ([loop, AppControllerImpl.h#L339-L400](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L339-L400)).
- StackChan's avatar/motion tick runs every 20 ms under the LVGL lock, but **adds 100 ms extra sleep whenever the xiaozhi voice agent is non-idle** ([_stackchan_update_task, hal.cpp#L145-L176](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/hal/hal.cpp#L145-L176)) — the face intentionally degrades to ~8 Hz to protect Opus encode/decode and the network path.

**Lesson for us.** Both mature projects treat face frame rate as the *shock absorber* for audio/network load. Interaction-aware timer periods were added first, but the panel's physical limit ultimately required backpressure at the lower transfer seam: 35 ms minimum between QSPI submissions. With two 110-row regions per face this caps actual rendering near 14.3 FPS while Wi-Fi/TLS is resident. The resulting network build keeps audio responsive, WSS connected, internal RAM stable, and the panel physically visible. Any future attempt to recover frame rate must preserve that measured panel envelope rather than merely changing the LVGL timer.

| m5stack/StackChan | esp_lvgl_port task, prio 3, pinned core 1 ([stackchan_display.cc#L121-L127](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/hal/board/stackchan_display.cc#L121-L127)); avatar task also core 1, prio 3 ([hal.cpp#L200](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/hal/hal.cpp#L200)) | xiaozhi audio tasks (external, core 0 by its defaults) | UI world and audio world segregated by core; all avatar mutation happens under the LVGL lock, including from MCP tool callbacks ([hal_mcp.cpp#L28-L40](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/hal/hal_mcp.cpp#L28-L40)) |

StackChan also demonstrates the memory ceiling bluntly: the launcher app framework is **fully torn down before the voice agent starts and never returns** ("Start xiaozhi, never returns", [main.cpp#L29-L62](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/main.cpp#L29-L62)) — the UI framework and the AI audio stack do not coexist on an ESP32-S3 in their product. Our single-purpose firmware avoids this, but it is a warning against accreting optional subsystems into the streaming build.

## 4. I²S capture/playback structure

**chat-stick is a half-duplex reference — confirmed at HEAD, do not copy.** One `I2SClass` is torn down and re-begun to switch between 16 kHz capture and 24 kHz playback ([configureAudio, AudioService.cpp#L556-L609](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L556-L609)); `startRecording()` additionally **disables the speaker PA** during capture ([AudioService.cpp#L245-L267](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L245-L267)). This forecloses barge-in and AEC by construction. Two genuinely useful details in the same file: capture reads **stereo** slots and selects the louder channel per chunk because the ES8311 mic lands on one slot ([captureChunk, #L286-L326](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L286-L326)) — a symptom to remember if our RX channel ever sounds halved or silent — and playback duplicates mono into both slots at write time ([playAvailableChunk, #L717-L780](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L717-L780)). Our `esp_codec_dev` duplex path at a single 24 kHz rate (`offline_echo.c:119-146`) is already the better structure.

**StackChan runs true full duplex at 24 kHz in/out on one I²S TDM port** with a dedicated capture codec exposing a **playback reference channel for AEC** (`input_reference`, ES7210) separate from the power amp ([cores3_audio_codec.cc#L9-L70](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/hal/board/cores3_audio_codec.cc#L9-L70), [config.h#L9-L10](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/hal/board/config.h#L9-L10)). Our single ES8311 has no hardware reference channel; this is concrete evidence for final-plan's caution that Phase 8 AEC on this board is unproven, not merely untested.

## 5. Push-to-talk buffering, short-tap handling, turn lifecycle

chat-stick's turn machine ([constants, AppController.h#L62-L102](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppController.h#L62-L102)) is the piece to adopt for Phase 3/4:

- **150 ms commit threshold with a pre-commit ring.** Capture starts on press, but nothing is sent until the press survives `kRecordingCommitMs = 150`; meanwhile up to 2×100 ms chunks are held in a drop-oldest ring and replayed to the server on commit ([bufferPreCommitAudio #L1509-L1530](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1509-L1530), [commitRecording #L1475-L1497](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1475-L1497)). No audio is lost and accidental taps never reach the server ([stopRecording #L1443-L1473](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1443-L1473)). Our current 180 ms *post-hoc* discard (`offline_echo.c:305-308`) rejects the clip but has no ring; when the relay exists, restructure to capture-then-commit so the first 150 ms still reaches the provider.
- **750 ms playback prebuffer with an escape hatch.** Playback starts when 36,000 bytes (=750 ms of 24 kHz PCM16, `kMinPlaybackBytes`) are queued **or** the turn is complete with any audio buffered, so short replies don't wait ([processPlayback #L1600-L1625](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1600-L1625)). Final-plan's decision to make this threshold configurable and test 100/250/750 ms stands; the escape-hatch condition should be copied exactly.
- **Turn-complete only counts after audio.** `noteTurnComplete()` ignores the signal if no audio arrived — it's stale from an interrupted prior turn ([TurnController.cpp#L58-L64](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/TurnController.cpp#L58-L64)); exit-to-Ready is only allowed from Playing ([#L1615-L1622](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1615-L1622)). Adopt both guards.
- **Thinking timeout** (15 s) flushes playback and returns to Ready ([#L1627-L1646](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1627-L1646)); transcript deltas are deduplicated against cumulative partials ([TurnController.cpp#L99-L129](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/TurnController.cpp#L99-L129)).

## 6. Mute, cancellation, and interruption

- A new press calls `_audio.stopPlayback()` **locally and immediately**, before any server round-trip ([startRecording #L1414-L1441](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L1414-L1441)); `stopPlayback()` zeroes the ring cursors and in-flight flag under the playback mutex ([AudioService.cpp#L538-L549](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L538-L549)).
- The server's `drop_audio` control message flushes any queued tail **without changing app state**, since the user is already mid-recording ([onDropAudio #L134-L140](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/app/AppControllerImpl.h#L134-L140); wire dispatch in [LiveSessionService.cpp#L690-L757](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/common/src/services/LiveSessionService.cpp#L690-L757) — binary frames are audio, JSON is control). This local-flush + server-flush split is exactly final-plan §4's cancellation design; the HEAD code confirms it works with a ~20 ms playback chunk granularity ([AudioService.cpp#L13-L17](https://github.com/steveruizok/chat-stick/blob/3321c9bfc9771ee8b3adc4815f6c72890d3db125/devices/firmware/waveshare/src/services/AudioService.cpp#L13-L17)).
- Our `offline_echo` mute already does the right local things (urgent front-of-queue command, output muted, buffers cleared, `offline_echo.c:318-329,462-472`) and the bringup log correctly flags that the codec input still clocks while "muted" — neither reference offers a hardware-grade mic mute either; StackChan's is a codec `EnableInput(false)` ([audio.cpp#L83](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/hal/audio.cpp#L83)).

## 7. Mouth animation and the modifier architecture

Neither current reference derives mouth motion from playback samples. chat-stick's Waveshare UI is text-only. m5stack/StackChan's `SpeakingModifier` flips the mouth open/closed every 180 ms with **random** weights (40–80 open, 0–20 closed) and no audio coupling ([speaking.h#L15-L90](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/stackchan/modifiers/speaking.h#L15-L90)), attached/detached purely on the agent's speaking status ([SetStatus, stackchan_display.cc#L480-L568](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/hal/board/stackchan_display.cc#L480-L568)). Our RMS-envelope mouth (`offline_echo.c:219-269` → `face_set_mouth_level`) is strictly better; keep it and do not regress to status-driven flapping when the audio moves server-side.

What *is* worth adapting from StackChan is the **modifier lifecycle**: modifiers are pooled objects with optional lifetimes that can self-destroy and restore state on exit (blink restores backed-up eyelid weights before destroying itself, [blink.h#L18-L118](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/stackchan/modifiers/blink.h#L18-L118); pool update in [stackchan.h#L126-L145](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/stackchan/stackchan.h#L126-L145)), and remote/model input reaches the face only as clamped typed parameters through a JSON schema ([json_helper.cpp#L16-L68](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/stackchan/json/json_helper.cpp#L16-L68)) or MCP tools with range-limited properties ([hal_mcp.cpp#L42-L70](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/hal/hal_mcp.cpp#L42-L70)). This matches final-plan §3's "composable, bounded modifiers" and is a good template when our monolithic `render_face()` grows past two or three more behaviors. Their default blink cadence at HEAD is ~5.2–5.7 s open / 200 ms closed ([blink.h#L25-L38](https://github.com/m5stack/StackChan/blob/b72b3ede38b32d54f0b6ba51c62cfcef2ec3ae1e/firmware/main/stackchan/modifiers/blink.h#L25-L38)) — slower than the 2.5–4.5 s our plan quotes from the community project; both are just tuning seeds.

## 9. Actionable recommendations

1. **Keep panel-buffer ownership explicit**: the completed CO5300 diagnostic and production driver count submitted/completed QSPI transfers and do not release the single partial draw buffer before `on_color_trans_done`. Keep overlap/error telemetry as a regression guard; do not treat `lv_draw_buf_flush_cache()` as evidence unless its handler is non-null.
2. **Adaptive face cadence** (Phase 2→3 boundary): make the frame period state-dependent and drop the face rate while streaming/duplex audio is active, following chat-stick's 90 ms playback gate and StackChan's non-idle throttle. Measure FPS and I²S error counters at each level.
3. **Drain committed capture to transport** (Phase 3): the local path now has a 220 ms pre-commit ring, commits at 180 ms without losing initial audio, rejects short taps, and interrupts playback locally. Connect the committed capture ring to the network sender without accumulating complete cloud turns.
4. **Copy the playback-gating conditions exactly** (Phase 4): start at configurable prebuffer **or** turn-complete-with-audio; accept `turn_complete` only after audio; leave Playing only from Playing; add a Thinking timeout that flushes buffers.
5. **Keep local-first cancellation**: press → local ring flush immediately; server `drop_audio` flush without state change; both references and our plan agree.
6. **Keep the RMS mouth; adopt the modifier-pool shape later**: when face behaviors multiply, move blink/breath/saccade/speaking into StackChan-style self-terminating modifiers over the existing parametric state rather than growing `render_face()` switch arms.

No firmware or plan files were modified as part of this research.
